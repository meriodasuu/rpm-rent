# Подключение VK Рекламы

Подготовлена интеграция пикселя VK Рекламы на основе очереди `_tmr` и загрузчика `https://top-fwz1.mail.ru/js/code.js`. Получен базовый код пикселя **3794185**: очередь и загрузчик совпадают с интеграцией. ID записан в `.env.local` и `.env.example`. Настройки перенесены в `.env.production` на сервере; приложение пересобрано и запущено для обоих доменов 21.09.2026. Пустой ID отключает пиксель. Блок `noscript` не добавлен: он отправлял бы запрос без согласия посетителя.

## Включение на рабочем сайте

1. На сервере установить `NEXT_PUBLIC_VK_PIXEL_ID=3794185` в `.env.production`; для другого хостинга — в переменных окружения сборки. Второй скрипт параллельно не вставлять.
2. Установить `NEXT_PUBLIC_VK_LEAD_GOAL=lead`. Присланный файл содержит только базовый пиксель и не подтверждает настройку цели. В кабинете создать JS-событие с точно таким же именем и категорией оформления заявки. Именно его использовать как основную конверсию.
3. Использовать один пиксель **3794185** для **rpmrent.ru** и **rpm-rent.ru**. Оба домена обслуживаются одним приложением, поэтому конфигурация общая. Просмотры отправляют фактический домен страницы; согласие посетителя хранится отдельно на каждом домене. Проверить приём событий с обоих доменов в кабинете VK.
4. Пересобрать приложение: значения `NEXT_PUBLIC_*` встраиваются во время сборки. Dockerfile и production compose уже передают новые build args.
5. Проверить реальную доставку в кабинете VK по сценарию ниже. До этого интеграция считается подготовленной, но не проверенной с реальным пикселем.

## Поведение

- Пиксель включается только после существующего согласия на аналитику; без ID, при отказе и на `/admin` новые события не отправляются.
- Просмотр отправляется при открытии публичной страницы и переходах между страницами Next.js. В передаваемом URL оставлен путь без параметров запроса.
- `lead` отправляется после успешного сохранения короткой заявки или обычной заявки на бронирование. Повторный ответ с тем же ID не отправляет вторую конверсию в этой сессии. Перезагрузка страницы благодарности не является конверсией.
- `phone_click`, `telegram_click`, `max_click`, `whatsapp_click` — отдельные вспомогательные события при наличии соответствующих кнопок; не считать их отправленными заявками.
- В собственные события VK не включаются телефон, имя и текст обращения. ID заявки используется только локально для защиты от дублей.
- Аналитика может блокироваться браузером; заявка всё равно сохраняется. Гарантировать совпадение количества заявок в базе и событий пикселя нельзя.

## Реклама и заявки

Рекомендуемая ссылка: `/cars/<slug>?utm_source=vk&utm_medium=cpc&utm_campaign=<campaign>`.

Распознаются источники `vk`, `vk_ads`, `vkontakte` без учёта регистра либо непустой `rb_clickid` при отсутствии UTM-источника. Явный `utm_source` имеет приоритет над click ID. Новая размеченная кампания заменяет предыдущую атрибуцию в сессии. Для VK открывается та же короткая форма, что для Директа. Источник сохраняется как `vk_ads`, отображается в админке, поиске и Telegram как «VK Реклама». Для поля `Lead.source` уже используется строка, новая миграция БД не требуется.

## Проверка перед запуском

1. Без согласия и без ID убедиться в отсутствии сетевых запросов пикселя.
2. После согласия открыть каталог и карточку через внутренние ссылки; проверить просмотры без дублей.
3. Перейти по ссылке с `utm_source=vk`, затем на другую карточку: короткая форма должна сохраниться.
4. Отправить одну тестовую заявку: проверить `vk_ads`, UTM и `rb_clickid` в сохранённой записи, подпись VK в админке и Telegram, одно событие `lead` в кабинете.
5. Проверить ошибки валидации, повторный ответ по тому же запросу, обновление `/spasibo`: новых конверсий быть не должно.
6. Повторить успешный сценарий обычной формы бронирования и существующий сценарий Яндекс.Директа.

Проверка Telegram на рабочем окружении отправит настоящее уведомление менеджерам: выполнять согласованно при финальном запуске.
